# CLAUDE.md: working on OpenStrategy Studio

A Streamlit app in which a person defines a trading strategy without code, then backtests and optimises it on vectorbtX (`vbt.x.SingleBacktest`, `vbt.x.PortfolioBacktest`) and vectorbt 1.1.0. All five phases of the implementation plan are written, and **phase 0 has been run** against the real libraries (vectorbt 1.1.0, vectorbtX `ace29e2`, then re-run on `16293a2`, `9f4cf54` and `9fa427e`, which fix everything phase 0 and its follow-ups found): the suite and `selfcheck` pass. `docs/VERIFY.md` is the record of every answer and every change it caused; `docs/UPSTREAM.md` lists what was found in vectorbtX and how each item was fixed. See "Status and next steps" below before starting.

## Commands

```bash
uv lock                          # once, if uv.lock is missing; commit it
uv sync --extra marsopt --extra desktop   # name every extra each time: a plain `uv sync` removes them
uv run pytest -rs                # -rs lists skips; with every extra installed only the bash check skips on Windows
uv run pytest tests/test_engine.py -x -q
uv run openstrategy-studio       # the app; also: desktop, selfcheck, worker <dir>
run.cmd                          # Windows: the same with both extras; arguments pass through (run desktop)
uv run openstrategy-studio selfcheck --quick
uv run python -m openstrategy_studio.indicators   # rewrite indicator_catalogue.json after a TA-Lib, pandas-ta or ta_patterns bump
```

Never `pip install`. Add dependencies with `uv add`.

**Found on 19 November 2026: the leverage cap cuts exits (`docs/UPSTREAM.md` issues 32 to 34, open).** The owner's JMA cross on SPY, bought outright at 1x with a whole account per trade, gave 4 trades in 16 years, the last open from 2010. Cause: vectorbtX passes `max_size = leverage × init_cash / price` on every bar, and vectorbt applies `max_size` to every order, closes included. So an exit worth more than leverage × the starting cash is cut short (32), positions never grow with the account under `risk_of` (33), and cut orders land off the increment (34). A remainder below the minimum size is never sold, and no entry is taken while it is held. Every whole-account or `risk_of` sizing near its leverage limit is affected, and so is the weights route when a grown holding is sold down. The Studio's pipeline matched plain vectorbt on that run once the cap was left out (same signals, order dates and sizes). No Studio workaround. Fixed in the vectorbtX checkout on 20 November 2026 (uncommitted): entries are capped at `leverage x` the equity at their signal bar, on the size step, and no exit is ever cut; the JMA run now makes 263 round trips with every sizing.

## Code style (the owner's rules; they override your defaults)

1. **Functional, no classes.** Use functions and plain dicts and lists. No dataclasses, no pydantic. The only classes are the ones vectorbt and vectorbtX provide. Where a library wants an object (BUTChC's executor), use `types.SimpleNamespace`.
2. **Do not over-modularise.** A helper earns its place only when it is called from three or more places, or the function would otherwise exceed about 100 lines. A reader should follow a feature top to bottom in one file.
3. **Explicit over clever.** Registries are dict literals. Prefer a visible `for` loop to a dense comprehension chain.
4. **Comment heavily.** Explain the why. Mark anything that can silently give a wrong number with `# ⚠️`, and anything unverified with `⚠️ VERIFY`.
5. **Few exception cases.** Validate once at the boundary: loading a spec, an import, the user pressing Run. Pages have ONE `try/except`, via `ui.run_guarded`. Do not wrap calls that cannot fail.
6. **Keyword arguments** at every vectorbt and vectorbtX call site.

UI text: sentence case, plain verbs, and errors that say what to do. No ALL-CAPS labels.

## Invariants: do not break these

* **A new session starts blank.** `ui.boot` seeds `spec.blank_spec()`, never a template. Templates and last time's draft are offered (Home, the Build page's Start from), never loaded on their own. Every page must render a blank strategy (no symbols) without an error or a change; `tests/test_app.py` renders it beside the templates.
* **One source of truth.** `st.session_state["spec"]` is the spec. Widgets are seeded from it on every run and write back through `ui.set_value`. Keys come from `ui.key(path)`, which includes a revision number that `ui.replace_spec` bumps.
* ⚠️ **A structural change renews every widget.** Adding or removing a condition, a feature or a variable, or switching a kind, calls `ui.renew_widgets` (inside `ui.rerun_after`): Streamlit keeps a keyed widget's own state, so without it the logic line keeps its old text and a reused letter shows (and writes back) a deleted condition's settings. `tests/test_app.py::test_build_steps_edit_the_spec` drives this.
* **Every value is a literal; ranges live in `optimise.variables` only,** keyed by the value's dotted path. `apply_params` writes a trial's values at those paths, drops `optimise`, and resolves every `{"choose", "options"}`, so the compiler never sees a range. Write variables directly (their keys contain dots), never through `set_path`. The Optimise page is the one place that adds one (the owner's call, 20 November 2026: a picker in each condition as well made it unclear where the choice is made); it offers exactly `tunable_inputs` and starts from `spec.default_variable`. A condition's card only shows what is searched. A change that removes a value calls `ui.prune_variables`, so no variable is left pointing at nothing.
* **One trading mode per strategy.** `setup.trading` is the vectorbtX mode; instruments carry none (`validate_spec` rejects one), and `engine.instrument_fields` adds it. A universe file keeps its own modes.
* **Every feature comes from the catalogue.** `indicator_catalogue.json` is generated, never edited: change the dict literals in `indicators.py` and rerun `python -m openstrategy_studio.indicators`; `tests/test_indicators.py` fails when the snapshot and the libraries disagree. Patterns come from ta_patterns only. pandas-ta's `offset` is never shown (a negative one is lookahead).
* ⚠️ **No catalogue entry looks ahead.** `test_no_entry_looks_ahead` computes every entry on full, truncated and different-future data; a failure goes to `EXCLUDED` with its reason (and upstream when it is a library's bug), never into the menu.
* **The logic line is parsed, never evaluated,** and brackets are required where two different operators meet. Every condition must appear in it.
* **Order timing masks signals on their own bar** (good for the day, flat by the day's end): never a shift. They are approximations until vectorbtX has the orders (`docs/UPSTREAM.md` issue 20).
* **The compiler shifts no signal.** The front door shifts entries, exits, short entries, short exits and the schedule to the next bar's open itself (vectorbtX `16293a2`), and a stop or target frame from a line with them (`1de5744`, `2b2d090`). A shift in `compile_signals` or `export_script` would delay them two bars.
* **Always the four-array form.** Never `direction="both"`.
* ⚠️ **A stop's and a target's kind says whether there is one, and its unit how it is measured; never the dict.** Each is `{"kind", "unit", "points", "pct"}`, plus `"multiple"` and `"line"` once measured from a line, and keeps every distance while it is off (`kind: "none"`) or measured another way, so the optimiser can switch it (a unit is offered only where the node holds what it needs). Read `(risk.get("target") or {}).get("kind") == "fixed"`, never `if risk.get("target")`, which is true for a target that is off. `validate_spec` rejects a stop or target with no kind; no unit is points.
* **Points go to vectorbtX's keywords, % to vectorbt's own, a line to per-bar frames.** `call_plan` sends a stop in points as `stop_points` or `trail_points` and a target as `target_points`; in % as `sl_stop` (with `sl_trail=True` when trailing) and `tp_stop`; from a line as the frames `compile.stop_lines` makes (`engine.STOP_LINE_ARGS`); never two forms for one leg. ⚠️ A per-bar frame is on the signal bar and unshifted, like the signals: the front door shifts it (vectorbtX `1de5744`; before that it read a per-bar `sl_stop` at the fill bar, lookahead). ⚠️ A multiple is a distance in price sent as points, so it is divided by the point value (point size x the conversion rate, `compile.point_value`), which vectorbtX multiplies back. A trailing stop in points stays that many points behind the best price (issue 27, fixed).
* **Stops are measured from the fill, pay the spread, and are checked on the entry bar.** vectorbtX's front door sets `stop_entry_price="price"` and `stop_exit_price="stopmarket"` and splits each bar into its open and the rest of the bar whenever a stop or target is active. `call_plan` must not pass either price; vectorbt's own defaults anchor stops at the entry bar's close and fill them with no slippage. The extra exits' callbacks run on the split bars too, through vectorbtX's bar view (called once per bar at the open, with bar indices): ⚠️ keep `exit_rules.py` templates written for whole bars, indexing their own arrays by `c.i`.
* **An FX pair never uses `SingleBacktest`.** `call_plan` routes any instrument with a base currency through `PortfolioBacktest(instruments=...)`, which keeps every field on the instrument. The reporting currency (`account.base_currency` in the spec) is passed as `account_currency=`, never `base_currency=`: on FX terms vectorbtX reads a flat `base_currency=` as the pair's base.
* **The benchmark is `pf.benchmark_value()`.** Never a second front-door call with no signals: that hold is funded at buying power (30x on an FX spread bet). Never pass `benchmark_rets=` to `returns_stats`.
* **Select one column as `pf[[column]]`.** It returns the same one-column shape a single run does. (The scalar form crashed every metric on a leveraged portfolio until vectorbtX `16293a2`.)
* **Every rule takes every condition kind, exits included** (the owner's call, 17 November 2026, replacing "never filter exits"). A weekday, month, session or higher-timeframe condition is an ordinary condition joined by the logic line: "A or Friday" is a time exit, "A and the week is down" narrows A as any "and" does. A stop, a target and the extra exits close a position whatever an exit rule says.
* **A condition's timing is history only.** `for_bars`, `within_bars` and `bars_ago` (at most one, `spec.TIMING_KEYS`) are applied by `compile.held`, a rolling window ending at the current bar or a forward shift; the export mirrors it (`held()` in the script). On a higher-timeframe condition the timing rides with the comparison and counts higher bars, before the shift to completed bars. Calendar conditions take none. `tests/test_lookahead.py` checks all three.
* **Cash across symbols is always named.** For a rule strategy on two or more symbols (`spec.cash_model`), `call_plan` passes `cash=` (default `per_instrument`), plus `entry_priority=` when shared. Never pass `cash_sharing`, `group_by` or `call_seq` through `engine_extra`; `validate_spec` rejects them. A feature priority is a score frame from `compile_signals`, unshifted like the signals.
* ⚠️ **What a trade too big to fund does is named on every rule strategy.** `call_plan` always passes `when_cash_short=` (`spec.when_cash_short`: the spec's choice, else `skip` in a shared account and `partial` otherwise, vectorbt's own default, which the golden numbers were made with). "Too big" includes leverage: a risk-sized trade with a tight stop can outgrow cash x leverage on one symbol. One widget sets it, the Risk tab's; the Account tab only says what it is.
* **Leverage is per instrument, in the grid, filled in with the usual limit** (the owner's call, 17 November 2026: one book can mix an index at 10x, a stock at 5x and an FX pair at 30x). `engine.usual_leverage`: unlevered unless it is a spread bet or a CFD traded on signals, which get the retail limits (30x FX, 10x indices and commodities, 5x single stocks, vectorbtX's table); everything else is 1x, no borrowing: bought outright, FX spot, and every portfolio ("most portfolios and naked trading are non-margin"; naked means buying the instrument itself, a share, a gram of gold, a currency, not a spread bet or CFD on it). That is vectorbtX's own table since `1de5744` (issue 24), which `usual_leverage` reads; the portfolio rule is the Studio's. Switching the way of trading or the kind of strategy, changing an asset class or quote currency, or adding a symbol fills it in, unless it was typed in by hand (`follow_usual` on the Build page).
* **Every instrument cell starts at its usual value** (the owner's call, 20 November 2026: no blank cells, even where the value is 0 or false). `engine.usual_instrument` is the one source: what a new symbol gets, what follows a change of mode, kind, asset class or currency, and what **Fill in the blank cells** writes. Each value is what a blank runs as: vectorbtX's own, or, for leverage, the point size and slippage, the Studio's, which `engine.instrument_fields` names for a blank. The market (asset class, currencies, read from the ticker) is the exception: a blank leaves it unknown. Keep it that way, so filling a cell never moves a result (`tests/test_engine.py::test_the_usual_instrument_fills_every_cell_and_runs_as_blanks_do`). ⚠️ A test that models a cost-free market names `slippage: 0.0`, since a blank is the usual slippage.
* **Slippage is shown and typed in %, kept as a fraction.** The grid converts both ways (0.02 shown is 0.0002 in the spec, vectorbtX's unit) and nowhere else does; "auto" passes through. The grid writes back only the cells a user changed, so rendering an older spec with blanks changes nothing.
* **Position size is what sets it and how much.** A fixed size (`stake`), a value (`notional`, or `notional_pct` with `risk_of`), or a risk (`risk_amount`, or `risk_pct` with `risk_of`); `risk_of` is `balance` or `equity` and a share must name one. A share of the starting cash would be a fixed amount again, so it is not offered (the owner's call, 20 November 2026). Switching carries the money across at the starting cash (1% becomes 100 on 10,000).
* **The point size is filled in the same way, by the market's convention** (`engine.usual_point_size`): the pip for the quote currency on FX (vectorbtX's `fx_pip`), 1.0 on an index or a share priced in pence (`GBp`), 0.01 otherwise. ⚠️ A blank one is named by `engine.instrument_fields` too, so `point_sizes` (the extra exits' stop distances) always agrees with the run; it used to fall back to 0.01 on an FX spread bet while vectorbtX used the pip. `engine.point_meaning` says what a point is in each market's words, under the grid and the stop and target boxes. ⚠️ A blank leverage is the usual one too: `engine.instrument_fields` names it, so the plan and the export always say it. The Risk tab only summarises it (read-only: a second widget on the same value would fight the grid) and says where it is set.
* **The trade-size check is vectorbtX's own sizing.** `engine.sizing_check` reads the stops with vectorbtX's `stop_plan` (from the plan's own arguments and `compile_signals`' frames, so every unit is read as the run reads it, and an entry whose level is rejected is left out), sizes the largest entry with `resolve_size` and `quantize_engine_size` at the entries' fill bars, and compares the stop with the bars' usual range. With risk sizing and no stop it shows the implied stop (1 / leverage of the price), marked `implied_stop`. A share of the balance or equity is estimated from the starting cash.
* ⚠️ **A spread bet's price is never converted.** Its stake is money per point in the account currency, so its profit is stake x points whatever the market's currency; converting the price would multiply that by the rate (vectorbtX's D4). `engine.conversion_quotes` gives a spread bet the account currency (rate 1) and converts the rest; `prepare_data` and the export both use it. Everything in points on a converted price is priced at point size x rate by vectorbtX (issue 29).
* **Separate accounts are reported as accounts.** `analysis.stats_tables` regroups ungrouped columns into one book of N x `init_cash` (vectorbt's `stats()` would average them silently); `per_symbol_table` shows each account. Never show the average.
* **No higher-timeframe leakage.** The filter needs `label="left", closed="left"` and then `.shift(1)`. `tests/test_lookahead.py` uses dense truncation cut points; keep them dense.
* ⚠️ **The leverage budget is named on every portfolio, True or False.** The front door defaults `leverage_budget` to True, so leaving it out applies it. It exists on the weights route only: a rule strategy never passes it, and `validate_spec` rejects one.
* **Portfolio weights stay full-shape.** Never forward-fill them. Always pass `schedule=` to `drifted_weights`.
* **One cost path.** Costs come only from instrument fields, never a raw `fees=` (it collides with commission and raises).
* **The borrow fee follows how a thing is traded.** `borrow_rate` belongs to equity mode only (a direct short borrows what it sells); a CFD or spread bet short pays its funding instead, and `validate_spec` says so. Never put a default rate in a template: none is published, and a blank one warns, which is the point.
* **Financing is one rule for every instrument:** the account's rates plus the Settings page's markup. There is no per-instrument financing (vectorbtX keeps the field reserved); `engine.instrument_fields` drops one an older spec holds, and the grid has no such column.
* **vectorbtX's warnings reach the page.** It reports what it could not price (a short borrowed for free, a carry leg with no currency) as Python warnings, which never reach Streamlit on their own. `run_backtest` collects each run's (`"always"`, or a long-lived server would show each once), `extract_results` keeps them in `meta["warnings"]`, and the Backtest results page shows them, each with the Studio's own hint under it (`analysis.WARNING_HINTS`, matched on vectorbtX's wording; `tests/test_engine.py` checks the match). Never silence or drop them.
* ⚠️ **`warnings.catch_warnings` is process-wide, so it runs under `engine.RUN_LOCK`.** Two runs at once (a second tab, or the start-up warm-up) would otherwise swap each other's warning lists.
* **The warm-up compiles numba's code at start, in the background.** `ui.boot` starts `engine.warm_up` once per process (every template on synthetic prices; no stored data, no network) unless the `warm_up` setting is off or `OPENSTRATEGY_STUDIO_WARM_UP=0` (which `tests/conftest.py` sets). The thread never calls Streamlit, and its failure is recorded, not raised.
* **A dataset is a name at a timeframe.** The catalogue's `symbol` column is the name strategies pick and the folder the bars sit in; `ticker` is the source's own symbol (a Yahoo refresh downloads it). `data.dataset_name_problem` refuses folder-unsafe characters and a name that differs from a stored one only in capitals (Windows folders ignore case). Storing under a name and timeframe held from another source asks first.
* **Charts.** `st.plotly_chart(fig, theme=None)` everywhere (via `ui.chart`). Every figure ends with `analysis.finish(fig, theme)`. The "page" chart theme is an ordinary template in plotly's registry: `analysis` registers it from the default page theme at import, and `ui.boot` re-points it at the page's own on every run.
* **The look lives in one place.** Colours, fonts, corners and spacing come only from the page theme file (`themes/<name>.toml`: `[theme]` for Streamlit, `[studio]` for the Studio's tokens) and the one stylesheet (`themes/studio.css`), which names no colour of its own, only `--os-*` variables. Pages set no colour and inject no CSS; anything that draws (charts, the diagram, a future canvas) reads the tokens through `style`. A page shows a section's colour by naming its tone: `ui.card(name, tone)` (a keyed container `os-card-<tone>-<name>`), `ui.sub_card`, `ui.section` (an expander keyed `os-exp-<tone>-<name>`), `ui.heading`; `studio.css` colours them from the theme's `tone_*` tokens by key. Midnight is the default page theme (20 November 2026). The stylesheet targets `data-testid` attributes, never `st-emotion-cache-*` classes.
* **The page theme is fixed per server start.** `cli.run_app` passes `--theme.base <file>` (never `.streamlit/config.toml`, which is read from the working directory) and records the file in `style.ACTIVE_ENV`; pages read that same file, so the stylesheet always matches Streamlit's colours. `st.set_option` cannot change theme options in 1.67, so a theme picked in Settings applies at the next start. A missing or broken theme file falls back to Daylight with a message; it never stops the Studio.
* ⚠️ **No `<` before a letter in the stylesheet**, even in a comment: `st.html`'s DOMPurify silently drops the whole `<style>`. `style.stylesheet` escapes `<` as `\3c `, and `tests/test_style.py` checks.
* **Export and in-app runs share one plan.** `export_script` and `run_backtest` both use `engine.call_plan`. `tests/test_export.py` keeps them equal.
* **Every setting has an ⓘ tooltip** (`help=`) that says what it does in plain words, checked against the code or the library it drives: a tooltip that misstates behaviour is worse than none. A collapsed label shows no ⓘ, so the heading beside it carries one. `tests/test_app.py` checks every page with every template.
* **Rendering must not change the spec.** A page rendered with defaults must leave the spec unchanged. Number widgets keep an integer range integer (`ui.param_input`).
* **Paths.** Use pathlib everywhere, never shell commands. All user data lives under `config.data_dir`.
* **Starting processes.** Use `cli.self_command`, which also works in a frozen bundle.
* ⚠️ **A job starts with no window and is judged dead only from outside.** `jobs.start_job` uses `CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW` on Windows, never `DETACHED_PROCESS` (a venv launcher's detached child opens a console window, and closing it kills the job). A worker that dies writes nothing, so `jobs.read_progress` decides: heartbeat quiet for `STALE_SECONDS` AND `process_alive(pid)` false. Never `os.kill(pid, 0)` on Windows: it terminates the process.
* **Files two processes share** (job folders) are written atomically with `jobs.write_json` / `jobs.write_parquet` and read through `jobs.retry_while_locked`: on Windows a file being replaced, or held open by the other process, briefly refuses access.
* **No HTTPS context before `config.apply_environment`.** On Windows, uv's CPython aborts the whole process when `SSLKEYLOGFILE` is set and any HTTPS context is created; `apply_environment` drops it. If a test run dies with no summary and `OPENSSL_Uplink` in the output, that is the cause.

## Testing conventions

Use plain pytest functions with no classes or mocking frameworks, and no network. Synthetic data comes from `tests/conftest.py::make_ohlcv`. Tests that need a library call `pytest.importorskip` inside the test.

## Known gaps

* The extra exits (time stop, breakeven, step trailing) need a fixed stop in points: their numba templates start from a distance in points per column (`exit_rules.runtime_values`).
* The instrument grid shows only the fields the strategy's trading mode accepts; it still cannot grey out single cells.
* Cap weighting and long/short selection are not offered: there is no market-cap source, and negative weights are unverified.
* Conditional spaces work with BUTChC and Optuna only; the other backends fix a rule at its version in use.
* Only the grid uses a variable's step; the other searchers pick any value in the range (whole numbers for a whole-number setting).
* The PyInstaller bundle is a spike (`docs/PACKAGING.md`). The first-run installer is the shipped route.
